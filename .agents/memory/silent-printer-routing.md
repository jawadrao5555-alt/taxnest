# Silent printer routing — durable rules

- **One-click enable prompt (owner mandate Jul 2026 — "solve for ALL customers", triggered by first-print stutter/truncation on cheap Windows drivers via browser printing):** sale-screen floating card (universal.blade.php, admin/manager-only, not pending) shows when `agent_enabled` + printers reported ≤7 days + silent OFF + `prompt_dismissed_at` NULL. Enable POST (`pos.api.printer-prompt`) recomputes `PosController::smartPrinterPick()` SERVER-side: thermal-looking name first (`pos|thermal|receipt|80|58|rp-|xp-|tm-`), else Windows default unless virtual (`pdf|xps|onenote|fax|journal`), else NULL → card links to Printer Settings instead (NEVER auto-pick blind — wrong device = receipts silently vanish, worse than popup). Enables receipt printer ONLY (KOT stays manual — wrong KOT device sends kitchen slips to the counter). `prompt_dismissed_at` lives in the `printerSettings()` normalized shape (POSTs rebuild from it — key would be silently dropped otherwise) and is ALSO stamped on any manual printer-settings save so deliberate-OFF shops are never nagged. Do NOT auto-enable server-side on printer report.
- **Receipt auto-print timing:** both receipt templates (80mm/58mm) wait for `document.fonts.ready` + 500ms with a 2.5s single-fire failsafe before `window.print()` — never fire print during page-busy rasterization (first-print truncation on cheap thermals); keep the 20s iframe chain signal untouched.

- **KOT `kot_printed_at` stamping happens at RESULT time, not render time** (agent path). `printJobContent` only records `printed_item_ids` on the job; `printJobResult` success stamps them (whereNull-guarded). **Why:** a physical print can fail after render (printer off/driver error) — render-time stamping made later delta tickets skip items the kitchen never saw. Popup/iframe path (`?auto_print=1` route) still stamps at render — that render IS the print there.
- Empty delta render (items already covered) → content endpoint returns **204**; agent marks job done without printing a blank page.
- **Electron `printHtml` must remove the `did-finish-load` listener in its done()** (removeAllListeners) — a stale `once` listener surviving a timeout fires on the NEXT job's load → duplicate physical print.
- Agent print options: `{silent, deviceName, printBackground, margins:{marginType:'none'}}` and **NO pageSize** — thermal drivers must keep their own roll setting.
- Templates auto-print only when `?auto_print=1` is in `location.search` — agent ≤v1.4.0 loads HTML via **data: URL**, v1.5.0+ writes a temp file + `loadFile` (file:// also has no query string, scripts stay dormant either way).
- **Data-URL 2MB cap (live failure Jul 2026, Pizza Master):** Chromium rejects `loadURL('data:...')` over ~2 MB with `ERR_INVALID_URL (-300)` — a 1.5 MB uploaded logo, base64'd into the receipt then base64'd again into the data URL, broke EVERY bill print (KOT without logo passed; shop saw "sent" tick because enqueue succeeds and failure is async on the agent). **Rule:** receipt blades must embed logos ONLY via `Company::receiptLogoDataUri()` (≤120 KB passthrough; bigger → cached 384px PNG in `storage/app/public/receipt-logos/`; unprocessable → null = print WITHOUT logo, never raw-embed). Agent-side `printHtml` (v1.5.0 source) uses temp file + `loadFile` so no size cap; deployed v1.4.0 agents stay data-URL — the server-side logo cap is what protects them.
- **Live GD is WEB-only:** `imagecreatefromstring` exists in cPanel's web PHP but NOT the ea-php84 CLI — warm/verify the receipt-logos cache via a web request (temp probe), never a CLI script (it will falsely report no GD). Once web-generated, the cache file is reused everywhere.
- Failed (status `failed`) jobs are never auto-retried — stale-requeue only rescues rows stuck in `printing`. After a fix, either flip rows to `pending` or have the shop reprint (Akhri Bills strip).
- Every silent path falls back to the classic popup/iframe on ANY enqueue failure (409 disabled/no_printer/agent_offline, network). Feature default OFF per company (`pos_printer_settings` JSON).
- `pos_kitchen` confined accounts needed `pos/api/print-jobs` added to the PosAuth allowlist — any new endpoint the KDS calls must be added there too.
- Print-succeeded-but-result-lost → stale requeue reprints after 2 min = ACCEPTED risk for bills; deltas are protected by the stamping design.
- **Bill enqueue double-press guard (Jul 2026, real shop incident):** laser + agent-poll latency ≈ 20s paper-out — cashiers press Print again and got a duplicate copy. `apiCreatePrintJob` bill branch dedupes: same transaction with a pending|printing job created within 2 min → return success + `deduped:true` (client shows a "wait" toast). Window is **created_at**-based so it never collides with the **updated_at**-based stale-requeue; 'done' jobs never match, so deliberate reprints stay allowed. KOT deliberately NOT deduped (multi-station fan-out + delta 204 already protects). `trySilentPrint` returns the payload object (truthy), never bare true — callers truthiness-check only.
- **"Popup showed despite silent print ON"** = usually a sale-screen tab loaded BEFORE the feature was enabled — `silentBillPrint` is baked into the page at load time; the shop must refresh the sale screen after changing printer settings.
- Dev testing gotcha: setting `agent_last_seen` via MySQL `NOW()` looks offline to Laravel (timezone mismatch) — use the real `/api/agent/heartbeat` endpoint instead.
- **Submission mode is DECOUPLED from agent connectivity (Jul 2026, real shop incident):** the /pos/agent "Direct Production" switch used to flip `agent_enabled=false`, which killed agent auth + silent printing for a live shop. Now the toggle flips `companies.agent_submits_pra` ONLY; `agent_enabled` = connectivity (auth, heartbeat, printing) and stays true. **Rule:** PRA SUBMISSION routing must read `Company::agentHandlesPra()` (fiscal_device ⇒ always true; else agent_enabled && agent_submits_pra??true), NEVER raw `agent_enabled`. `agent_enabled` remains correct ONLY for connectivity checks (AgentAuth, agentOnline, admin online/offline display) and FBR POS paths. In Direct mode `pendingInvoices` returns an empty set (`pra_mode=direct_server`) so a connected agent never double-submits. Do NOT make the toggle touch `agent_enabled` again.
- **KOT "ADDED ITEMS" banner ≠ delta param** (client bug Jul 2026): the universal screen sends `delta=1` on EVERY KOT incl. the FIRST — keying the banner on `$delta` alone stamps "ADDED ITEMS" on brand-new orders. Rule: banner only when the order has previously STAMPED rows (`kot_printed_at` NOT NULL) that are NOT on this ticket. Popup/iframe path is safe (stamping is a raw DB update after the items relation is eager-loaded — in-memory rows stay NULL within the request). KNOWN caveat: multi-station FIRST send via the agent can still misfire (station #1's result-time stamp lands before station #2 renders) — deterministic fix would pass an `addition=1` flag computed at ENQUEUE time; not done (near-zero multi-station users).
- **KOT Full Mode (customer feedback Jul 2026, opt-in `companies.pos_kot_full_mode`)**: restaurant complaint — delta ticket after an order update prints a tiny slip the kitchen misreads. When ON: delta request WITH unprinted rows renders the WHOLE order ("++UPDATED ORDER++" banner + per-row NEW badges on the unprinted ids); delta with NOTHING new must STILL render empty (204 agent / blank-guard browser) — that guard is what prevents duplicate slips, never bypass it. The two render paths (browser kitchen-ticket route, agent print-job content) must stay branch-identical. First-ever ticket stays clean (no banner/badges). Stamping stays whereNull-guarded on both paths, so already-printed rows keep their original batch; agent result-time stamping must set `kot_batch_no` alongside `kot_printed_at` (was silently NULL for months). Toggle lives on kitchen-settings ("Always Print Full KOT"), hasColumn-guarded for prod schema drift. With stations configured, a full-mode station-filtered ticket may show "ADDED ITEMS" instead of "UPDATED ORDER" — cosmetic, accepted.

## Waiter-punched orders (29 Jul 2026)
- Waiter storeOrder/appendItems now enqueue KOT via `App\Services\KotPrintService::enqueueForOrder` (best-effort, inside the same DB::transaction — jobs commit atomically with the order). Before this fix waiter orders only stamped kot_sent_at with NO print job (kitchen never printed).
- KotPrintService mirrors PosController::apiCreatePrintJob's KOT branch (no-station single job + station split, delta support) — if that branch changes, keep the service in sync. Station-PINNED KDS path stays only in the controller.
- Cashier settling a waiter-loaded order does NOT re-enqueue KOT (incomingOrderId path passes no KOT order id) — no double print.
- Toast types in universal.blade.php: success=green, info=blue (new), else red. Info banners must use 'info', not 'error'.

## Counter KOT Copy (Jul 2026)
- Printer Settings 3rd picker `counter_kot_printer` + `counter_kot_enabled` (normalized in Company::printerSettings). Copy fires ONLY for dine_in, as one extra type='kot' job (best-effort try/catch, never blocks kitchen), in PosController::apiCreatePrintJob + KotPrintService — NOT on station-pinned KDS path or transaction-based KOT branch. ## Print-job dedupe & retry (30 Jul 2026, Pizza Master)
- `trySilentPrint` (pos/universal) retries ONCE (1.2s) on network error/5xx — so `apiCreatePrintJob` now dedupes ALL types (bill AND kot/proof): identical pending/printing job < 2 min = return `deduped:true`, never a second physical copy. KOT key = order/txn + target_printer + render_query (counterCopy included).
- Dedupe is SAFE for delta KOTs: a pending job renders unprinted rows at PRINT time, so one queued job covers later fires.
