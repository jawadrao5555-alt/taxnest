Verdict: SAFE WITH IMPROVEMENTS
  (not SAFE AS-IS, not REQUIRES emergency pipeline fix before next deploy)

The #10 → #13 → #14 sequence is GitHub Actions concurrency + Environment
approval behaving as configured. It is mostly INTENTIONAL. One interaction
is a real pipeline design gap: a run that is waiting for production approval
occupies the concurrency group like an in-progress job, so it can delay the
newest deploy for hours and, if later approved, can still attempt an older
(non-tip) main SHA. Exact-SHA guards prevent rolling LIVE BACKWARDS. They
do not prevent deploying an intermediate SHA that is still ahead of live
HEAD. Elaan uniqueness accidentally blocked #10; that is not a substitute
for concurrency design.

1. EXECUTIVE SUMMARY
============================================================

Deploy Production uses:
  concurrency.group = production-deploy
  cancel-in-progress = false          # .github/workflows/deploy-production.yml:57-59
  jobs.deploy.environment = production  # line 65 (manual required reviewers)
  workflow_dispatch target_sha + push to main  # lines 34-52

GitHub semantics (documented by GitHub, confirmed by this incident):
  - At most ONE run in the group is "active" (running OR waiting for an
    Environment protection rule).
  - Newer runs that cannot start are PENDING.
  - When another run is queued into the same group, GitHub CANCELS the
    previously pending run with:
      "Cancelling since a higher priority waiting request for
       production-deploy exists"
  - cancel-in-progress: false means the ACTIVE run is NOT cancelled —
    including a run that is only waiting for Environment approval.

That is exactly #10 → #13 → #14.

#10 sat in Environment-approval wait for ~12h49m and held the slot.
#11, #12, #13 were each the pending successor and were cancelled when a
newer auto-dispatch arrived. #14 became the pending successor. After the
owner approved #10, #10 RAN (old SHA d39c3122) and failed the Elaan gate
before SSH mutation. #14 then got its own Environment approval and
successfully deployed exact SHA aecc864d (PR #28) over SSH and passed
ci-live-verify.

This is EXPECTED given the YAML. It is not a GitHub outage.

It is NOT "latest SHA always deploys first". The oldest still-active
approval request wins the SSH slot when approved. The newest pending run
wins among the queued (not yet active) runs.

3. CONCURRENCY MECHANICS
============================================================

File: .github/workflows/deploy-production.yml lines 57-59

  concurrency:
    group: production-deploy
    cancel-in-progress: false

Same group for:
  - push to main (human / non-GITHUB_TOKEN merges)          lines 35-37
  - workflow_dispatch (auto-merge handoff AND manual UI)    lines 38-52

So auto-deploy and manual deploy COMPETE in one group. Intentional
serialization (docs/ops/github-production-deploy.md lines 74, 20).

cancel-in-progress: false is INTENTIONAL and must not be flipped to true
without a different design: an in-flight live-remote-apply.sh holds
`flock`, `artisan down`, checkout, migrate, FPM reload. Cancelling that
mid-SSH is how you leave the site in maintenance (apply_fail_reason codes
91-99 in scripts/lib/live-remote-apply.sh).

GitHub pending-cancellation ("higher priority waiting request"):
  EXPECTED. It is how GitHub implements "only one pending successor".
  It already IS a limited latest-wins for the QUEUE, not for the occupant.

Can an old blocked/manual-approval deployment delay a newer one indefinitely?
  YES. Environment wait default timeout is long (GitHub default 30 days
  unless the Environment is configured shorter — PRODUCTION-ONLY to read
  the Environment timeout UI). Until the occupant is approved, rejected,
  or times out, the newest run stays pending.

Can a stale production deployment become a queue blocker?
  YES. #10 was exactly that for ~12h49m.

Do multiple manual dispatches safe or dangerous?
  Safe against overlapping SSH (one occupant).
  Dangerous as a UX: each new dispatch cancels the previous pending one,
  and none of them can start until the occupant (possibly an old SHA
  waiting for approval) finishes.
  Empty target_sha emergency dispatch pins github.sha AT DISPATCH TIME,
  not at approval time (deploy-production.yml lines 89-91). Approving it
  hours later still deploys that frozen SHA.

Does the system guarantee "latest intended main SHA eventually deploys"?
  NO guarantee.
  It guarantees: the newest PENDING run survives; the occupant runs to
  completion even if stale; after the occupant ends, the newest pending
  run may start (after its own Environment approval).
  If the occupant is never approved, the newest run never starts.
  If the occupant is approved and succeeds on an intermediate SHA, live
  moves there; then the pending newest run can still upgrade live IF it
  is allowed to run. If that newest run is then cancelled (another even
  newer dispatch) after the occupant already applied an intermediate SHA,
  live can sit on the intermediate SHA until a later successful deploy.

jobs.deploy.environment: production
  .github/workflows/deploy-production.yml:65

GitHub holds the job in status waiting until required reviewers approve.
Secrets PRODUCTION_SSH_PRIVATE_KEY and LIVE_QA_PASS are not available
until after approval (docs/ops/github-production-deploy.md:56-62).

Interaction with concurrency (from this incident + GitHub's model):

  Q: Does a run waiting for approval hold the concurrency slot?
  A: YES. Evidence: #11/#12/#13 never started a job (jobs: [] in gh run view)
     while #10 had no job steps until 06:51 — yet they were cancelled as
     pending, not run in parallel. #10 was the occupant the whole time.

  Q: Can another deployment overtake the approval-waiting run?
  A: NOT while cancel-in-progress is false. The pending successor cannot
     start. It CAN replace a previous pending successor (#13 cancelled by #14).

  Q: Can a newer run cancel an older waiting (approval) run?
  A: NOT with current YAML. It can cancel older PENDING runs only.

  Q: Is that safe for production?
  A: Safe against two SSH applies at once. Unsafe as an operator model:
     approving the oldest waiting run after main has moved still starts
     that oldest SHA. #10 did exactly that (d39c3122 while tip was aecc864d).

  Note: even if Elaan had passed, ci-deploy-production.sh:198-199 would have

Can a deploy get stuck behind an old run because Elaan is stale?
  Indirectly: the OLD occupant (#10) failed Elaan quickly once approved, which
  FREED the slot for #14. If #10 had used a unique title, it would have
  deployed the intermediate SHA first; #14 would still have followed.
  Elaan did not cause the 12-hour wait. Approval + concurrency did.

8. SCENARIO MATRIX
============================================================

Scenario 1 — SHA A auto-dispatch waits for approval; SHA B merges meanwhile

  Today: A remains occupant. B's dispatch is pending (or cancels a previous
  pending). A, if approved, may apply A (if live is still ancestor of A).
  Then B may apply B.
  Stale live: possible temporarily (A then B) or if B never runs.
  Older after newer: A can apply after B was already the intended tip.
  Operator: must approve/reject A; rejecting A unblocks B faster.
  Data safety: one-at-a-time SSH; no rollback past live HEAD.

Scenario 2 — A waits 12 hours; B dispatched  (#10/#14)

  Today: what happened. B pending. A approved → A attempts apply.
  Elaan may fail A (as here) or A may succeed on intermediate SHA.
  Stale: live stayed on #21 until #14; would have gone to #22 if Elaan passed.
  Operator: required (two approvals).
  Safety: preserved; #10 did not mutate live.

Scenario 3 — Manual deploy of old SHA while newer main exists

  If old SHA is behind live HEAD: REFUSED (ancestor check).
  If old SHA is on main, ahead of live, behind tip: ALLOWED by current
  guards (this is #10's shape). Operator can deploy a non-tip SHA.
  Classification: IMPROVEMENT RECOMMENDED (optional "must be origin/main tip"
  unless an explicit rollback workflow).

Scenario 4 — Two automatic deployments close together

  First becomes occupant (approval wait). Second pending. A third cancels
  the second. Only latest pending remains. Expected GitHub behavior.
  Both still need Environment approval in series.

Scenario 5 — Elaan missing for SHA A; SHA B is latest main

  A occupant fails gate after approval (no live mutate). B then runs.
  If A is pending not occupant, a B dispatch cancels A before it ever
  hits Elaan. Stuck queue is the occupant, not Elaan.
  Unnecessary manual work: owner had to approve #10 knowing main had moved,
  then approve #14. Elaan unique-title rule is extra work on every NEW SHA
  (intentional product rule, not a concurrency bug).

Scenario 6 — Failure after SSH mutation

  live-remote-apply.sh: artisan down first (line 58-59). On failure, site
  stays in maintenance (comments lines 60-61; apply_fail_reason 91-99).
  Fail closed. Operator must artisan up after fix. No automatic rollback
  (docs/ops/github-production-deploy.md:132; deployment/ROLLBACK.md).
  ci-deploy-production.sh treats non-zero apply as fail; live-verify skipped.

Scenario 7 — Deploy succeeds, live verification fails

  Workflow job fails at Post-deploy live verification
  (deploy-production.yml:156-163). Live HEAD may already equal TARGET_SHA
  (mutation done). Cloud Agents must start a new diagnosis cycle
  (docs/ops/cloud-agent-issue-to-live.md). Production is on the new SHA
  with a failed verify — not rolled back.

9. FINDINGS CLASSIFIED BY SEVERITY
============================================================

F1  Concurrency group production-deploy + cancel-in-progress false
    SAFE / EXPECTED for overlapping SSH protection.
    Must NOT be weakened to cancel-in-progress: true on the apply job.

F2  GitHub cancels previously pending runs ("higher priority waiting request")
    SAFE / EXPECTED. This is how #13 died and why only #14 remained queued.

F3  Environment-approval wait occupies the concurrency group
    IMPROVEMENT RECOMMENDED / HIGH PRIORITY PIPELINE BUG (operator model).
    Not a CRITICAL live-data bug: #10 did not mutate live; rollback past
    live HEAD is refused. But an approved stale occupant can delay the
    newest SHA for hours/days and can apply an intermediate SHA.

F4  No "must be origin/main tip" check
    IMPROVEMENT RECOMMENDED.
    Guard only requires SHA ∈ origin/main history
    (deploy-production.yml:127-132; ci-deploy-production.sh:141-142).

F5  Elaan #10 failure due to reused title + no re-date + NEW-SHA time gate
    SAFE / EXPECTED (elaan-freshness-eval.py; PR #11/#18 design).
    PR #22 shipped the same title as #21 (git show d39c3122:deploy/elaan.yml).
    That is a content mistake on that PR, caught by the gate.

F6  Elaan gate runs after approval and after taking the concurrency slot
    IMPROVEMENT RECOMMENDED (UX). A unique-title problem cannot dequeue
    an occupant. Not a safety hole.

F7  Exact SHA pin, main-history guard, live ancestor check, post-apply HEAD
    match, ci-live-verify HEAD match
    SAFE / EXPECTED. #14 proved the happy path. Must NOT be weakened.

F8  Auto-merge workflow_dispatch target_sha handoff
    SAFE / EXPECTED (enable-pr-auto-merge.yml; PR #16). All of #10-#14
    used it. GITHUB_TOKEN push suppression is real; this is the correct
    workaround.

F9  Auto-dispatch and manual dispatch share production-deploy
    SAFE / EXPECTED serialization. Combined with F3, manual and auto
    can block each other.

F10 Fail-closed apply (maintenance page, no auto-rollback)
    SAFE / EXPECTED. Must NOT add automatic rollback in the same job
    without a separate design.

F11 Empty target_sha emergency path uses frozen github.sha
    SAFE if documented; IMPROVEMENT if operators think it means "tip at
    approval time". deploy-production.yml:89-91.

F12 No CRITICAL PRODUCTION SAFETY ISSUE found in this incident.
    Live was not rolled back. Two SSH applies did not overlap. #14 landed
    the intended SHA and verified. Settings snapshot / allow_settings path
    unchanged; owner did not modify company settings.

10. RECOMMENDED FUTURE DESIGN (DO NOT IMPLEMENT HERE)
============================================================

Goal: keep one-at-a-time SSH, stop stale approval occupants from blocking
or applying non-tip SHAs.

Safest design sketch (evaluate, do not ship in this audit):

  1. Keep cancel-in-progress: false on the SSH/apply job. Never cancel
     an in-flight live-remote-apply.

  2. Split the workflow into two jobs:
       job "gate" — no environment secrets; concurrency group
         production-deploy-latest with cancel-in-progress: TRUE
         (or a dedicated "queue" group). This job only resolves SHA and
         asserts it equals origin/main tip (unless an explicit
         rollback input is set). Waiting for Environment should happen
         HERE or in a third "approve" job that IS cancellable.
       job "apply" — environment: production, needs: gate, concurrency
         production-deploy-apply, cancel-in-progress: false.

     Effect: a newer main SHA cancels the old approval-wait, not the
     in-flight SSH. This is the usual answer to questions 1, 2, 4, 6, 8.

  3. Add a tip check on non-rollback deploys:
       test "$DEPLOY_SHA" = "$(git rev-parse origin/main)"
     after fetching origin/main (question 3 and 7). Historical SHA
     deploys belong in deployment/ROLLBACK.md, not this workflow.

  4. Do not move Elaan before Environment approval unless a secret-free
     check is enough (committed unique title vs previous commit's title).
     Live COUNT still needs SSH. Evaluating committed-title-uniqueness
     in the cancellable gate job would have failed #10 before occupying
     apply (question 5, partial).

  5. Document for reviewers: if main has moved, REJECT the old
     Environment request instead of approving it.

  6. Optionally set a short Environment wait timer (GitHub UI, owner)
     so a forgotten approval cannot block for 12 hours. That is an
     Environment setting, not a YAML change — owner-only.

Questions from the prompt, answered without implementing:

  1. Latest-wins: YES for approval-wait / pending; NO for in-flight apply.
  2. Expire/cancel old approvals when main advances: YES, via cancellable
     pre-apply job or Environment timeout.
  3. Only latest main SHA deployable: YES for this workflow; rollback
     remains a separate documented path.
  4. Same concurrency group for auto+manual: YES for apply; a second
     cancellable group for the wait is the improvement.
  5. Elaan before concurrency wait: only a secret-free unique-title
     lint; live freshness still after SSH.
  6. Invalidate stale approval when main advances: YES (see 2).
  7. Prohibit historical SHA: YES on this workflow; not on rollback.
  8. One-at-a-time without stale blockers: YES, by splitting jobs as in (2).

This section is NOT part of the original read-only audit. It records the
narrow pipeline fix shipped after the audit verdict SAFE WITH IMPROVEMENTS.

Implemented changes:
  - Split Deploy Production into job "gate" and job "deploy".
  - Removed workflow-level concurrency (that was the approval-slot bug).
  - gate: no environment: production, no SSH secrets, concurrency group
    production-deploy-gate, cancel-in-progress: true.
  - gate requires requested SHA == current origin/main TIP (plus the
    existing ancestor/history guard).
  - After the tip check passes, gate cancels other Deploy Production runs
    whose GitHub status is exactly "waiting" (Environment approval). It
    never selects in_progress / queued / pending.
  - deploy: environment: production (approval + secrets UNCHANGED),
    concurrency group production-deploy, cancel-in-progress: false,
    needs: gate. Re-checks tip AFTER approval, BEFORE SSH.
  - scripts/ci-deploy-production.sh also requires origin/main tip BEFORE
    the SSH preflight / Elaan insert / remote_apply.
  - Historical SHA on this workflow is fail-closed with a diagnostic.
    Rollback remains deployment/ROLLBACK.md.

Tests:
  - scripts/tests/deploy-stale-sha-guard-check.sh (new)
  - scripts/tests/ci-deploy-production-check.sh (extended; nested)
  - scripts/tests/automerge-deploy-handoff-check.sh (extended)
  - scripts/tests/issue-to-live-check.sh (extended)
  - pr-checks.yml now runs ci-deploy-production-check.sh
  - php artisan test (full suite, run in the fix PR)

New deployment-state model:

  dispatch / push
       |
       v
  job gate (NO Environment, NO secrets)
       |  concurrency: production-deploy-gate, cancel-in-progress: true
       |  resolve SHA → checkout SHA → history guard → TIP guard
       |  if SHA != origin/main tip: FAIL (no approval request, no SSH)
       |  if SHA == tip: cancel other runs with status=waiting
       v
  job deploy (Environment production — MANUAL approval still required)
       |  concurrency: production-deploy, cancel-in-progress: false
       |  waiting for approval does NOT block a newer gate
       |  after approval: TIP guard again → Elaan → SSH apply → live verify
       v
  live HEAD == TARGET_SHA (still the tip at apply start)

Explicit statements:
  - Environment approval REMAINS enabled. It is not bypassed. Secrets stay
    on Environment production. The gate job cannot read them.
  - SSH/apply REMAINS serialized. cancel-in-progress is false on job deploy.
    In-flight live-remote-apply is never cancelled by this workflow.
  - Stale / non-tip SHA is FAIL-CLOSED before any production mutation
    (before Environment wait when detected at gate; again before SSH if
    main moved during approval).
