4. RETRY / IDEMPOTENCY BEHAVIOR
============================================================

NEW SHA (live HEAD != TARGET_SHA):
  published title T' = human [deploy TARGET_SHA]
  T' does not exist → ELAAN_INSERTED (new row, now())
  time_fresh_count >= 1 → PASS
  then remote_apply

SAME SHA retry (insert already done, apply not yet, live still old):
  T' exists → ELAAN_EXISTS, created_at unchanged
  if T' was created after last marker → time_fresh PASS
  apply still serialized / tip-checked

SAME SHA refresh after successful deploy (live == target == marker):
  T' exists, time_fresh usually 0 (row is before the new marker)
  same-SHA path looks up T' exactly → PASS
  no new row, no re-date

OLD human title (row #265) vs new SHA:
  published title is T' != #265.title

  cannot PASS

5. ADVERSARIAL REVIEW
============================================================

Q: Can an old AppUpdate satisfy a new deployment SHA?
A: No. NEW SHA requires time_fresh_count >= 1. Title-match is ignored
   on the new-SHA path. The insert uses a SHA-qualified title, so it
   cannot no-op against #265. Proven by elaan-deploy-sha-title-check.sh
   and elaan-freshness-eval.py new_sha_missing_fresh.

Q: Can the same SHA create duplicate announcements?
A: No. Same qualified title → ELAAN_EXISTS before AppUpdate::create.
   PHP model + helper static checks: no second row.

Q: Can a retry re-date an old announcement?
A: No. exists path does not update/touch/save. created_at stays.

Q: Can Elaan failure be bypassed before SSH apply?
A: No. Order remains insert_committed_elaan_spec → check_elaan_freshness
   → remote_apply. Freshness fail exits 1. skip_elaan still default false.
   (Insert itself uses SSH to run PHP; code apply does not run.)

Q: Does PR #29 stale-SHA protection remain intact?
A: Yes. deploy-production.yml unchanged: gate + tip equality,
   production-deploy cancel-in-progress: false, environment: production,
   no workflow-level concurrency. Static test asserts this.
