1. VERIFIED CURRENT STOCK ARCHITECTURE
================================================================

[VERIFIED] Two NestPOS stock ledgers, on purpose
  RecipeInventoryService class docblock:
    “Product stock and ingredient stock are deliberately kept as two
     ledgers: a recipe dish consumes its ingredients, while a product
     without a recipe consumes the normal product stock ledger.”

  Sale path: PosInventoryController::deductStockForInvoice
    - items with a recipe → RecipeInventoryService::consumeForInvoice
      (does NOT reduce pos_products / inventory_stocks)
    - items without a recipe → inventory_stocks.quantity +
      pos_products.stock_quantity mirror (company total)

[VERIFIED] Ingredient master is COMPANY-WIDE
  Table ingredients: company_id, code (nullable, no UNIQUE index),
  name, unit, base_unit, conversion_factor, cost_per_unit,
  current_stock (company mirror), min_stock_level, is_active
  Model: App\Models\Ingredient
  Unique (product_id, ingredient_id) lives on product_recipes, not on
  ingredients.name.

[VERIFIED] Ingredient qty per branch is a SECOND table
  ingredient_stocks unique (company_id, ingredient_id, branch_id)
  columns: quantity, min_stock_level ONLY
  NO avg_purchase_price, NO last_purchase_price, NO supplier_id
  Model: App\Models\IngredientStock

[VERIFIED] Finished-goods qty per branch
  inventory_stocks unique (company_id, product_id, branch_id)
  columns include avg_purchase_price, last_purchase_price
  NestPOS product_id values are pos_products ids (FK dropped;
  DI and POS companies isolated)

[VERIFIED] Movement ledgers
  inventory_movements types:
    purchase, sale, adjustment_in, adjustment_out,
    return_in, return_out, transfer_in, transfer_out,
    opening, recipe_sale, recipe_return
  extra transfer columns: transfer_status, received_quantity
  ingredient_movements types actually written:
    recipe_sale, recipe_return, ingredient_adjustment
    stock_check_in, stock_check_out  (StockCheckService)
  ingredient_movements has snapshot JSON, NO unit_price column

[VERIFIED] conversion_factor
  Stored on ingredients; RecipeInventoryService does not read it.
  Consume math is quantity_needed * sale qty in the ingredient's unit
  as written. kg vs g is NOT auto-converted.

[VERIFIED] There is no GRN table, no supplier_item map, no NestPOS
  purchase Excel, no receipt_control module.

5. BRANCH STOCK
================================================================

[VERIFIED] BranchStockService rules (inventory_stocks)
  No branches → branch_id NULL (single pile).
  With branches → every write keyed to a real branch.
  Sale/void use the BILL branch, not the session.
  writeBranchId(preferred):
    if not multi-branch → null
    else preferred if it belongs, else session stamp, else head office.
  viewingAllBranches: owner sees all; confined manager never sees all.
  FBR purchase from all-branches view is REFUSED (must pick a shop).
  healLegacyRows adopts NULL inventory_stocks onto head office.
  healLegacyRows does NOT touch ingredient_stocks or ingredient_movements.

[VERIFIED] Ingredient branch writes
  changeIngredientBranchStock:
    if !$branchId → return (single-shop uses current_stock only)
    if no row → INSERT quantity = $initialQuantity (often company
      current_stock) THEN apply delta.
  Ingredient adjust UI posts no branch_id, so multi-branch uses
  writeBranchId(null) → session branch or head office. Silent.

[VERIFIED] One ingredient (one master row) can have many
  ingredient_stocks rows (one per branch). Master is not duplicated.

[INFERRED] First kitchen movement on a multi-branch shop that still
has only current_stock (no ingredient_stocks row) can seed the active
branch with the FULL company qty then apply the delta. That is a
legacy-heal gap, unlike finished-goods healLegacyRows.

[PROPOSED] Bulk stock-in MUST require an explicit branch when the
company has branches, same refusal as FBR all-branches purchase.
Never inherit head office silently for a 1000-row file.

7. MATCHING OPTIONS
================================================================

What identity fields exist TODAY
--------------------------------
[VERIFIED]
  Ingredient: id, company_id, code (nullable), name, unit
  No barcode on ingredients.
  No supplier item code.
  Recipe Excel already matches ingredients by name+unit exact
    (strtolower trim), else name-only if unit blank.
  Product Excel / recipe product side: barcode → SKU → name.
  Stock-check Excel: Line ID, else exact item_code; duplicate code
    is ambiguous and refused (does not guess).

What a typical supplier file contains
-------------------------------------
  Supplier Item Code | Supplier Item Name | Qty | Unit | Rate
  (example in the brief: RICE-25, Basmati Rice, 500, kg, 300)

[PROPOSED] Match order for STOCK-IN (not master import)
  1. Exact Ingredient Code, case-insensitive, company-scoped.
     If two ingredients share a code (possible: no DB unique) → UNMATCHED.
  2. Exact name + unit (same key as recipe import: name|unit).
     If name matches but unit differs → UNMATCHED (do not convert).
  3. If the row also has a NestPOS barcode/SKU it is a PRODUCT row,
     not an ingredient — route to finished-goods adjust, never to
     ingredients.
  4. Never primary-match on fuzzy name, supplier name, or rate.

  Do NOT use supplier item code as primary identity until it is stored
  on the ingredient (see §9). On first clearance, writing the supplier
  code into empty ingredients.code reuses an EXISTING column and makes
  the next file auto-match at step 1.

[VERIFIED] Fuzzy matching is not used anywhere in current importers.
Do not introduce it as primary identity.

[UNKNOWN] Whether shops already put supplier codes into ingredients.code.

8. CLEARANCE WORKFLOW
================================================================

[VERIFIED] Closest existing patterns
  Recipe import: skip bad rows, auto-create missing ingredients, commit
    the rest. No human clearance queue.
  Product import: skip/error messages, no staging table.
  Stock-check: Line ID sheet → review gaps on screen → explicit Post.
  FBR purchase: operator picks products in the UI (identity is product_id).
  HS unmapped queue exists for tax HS codes (create_hs_unmapped_queue) —
    that is FBR HS, not inventory.

[PROPOSED] Stock-in clearance (workflow only; posting uses existing
adjustIngredientStock / adjustStock)

  Upload Excel
    → parse, do not post
    → each row: MATCHED | AMBIGUOUS | UNMATCHED | INVALID
    → operator:
         MATCHED: confirm
         AMBIGUOUS/UNMATCHED: pick existing ingredient OR send to master
           (do not create from the stock file)
         INVALID: qty/unit/branch errors stay unposted
    → Review totals (qty × rate, branch)
    → Clear / Post
    → each posted line calls the EXISTING adjust service once
    → unposted lines remain on the review list

  Confidence:
    exact code = high
    exact name+unit = high
    name only = never auto-post (recipe import’s name-only fallback is
      too loose for stock)

[PROPOSED] Do not auto-post on upload. Stock-check already taught the
shop “import counts, then Post”. Reuse that mental model.

10. COST HANDLING
================================================================

[VERIFIED] Ingredient cost today
  Single field: ingredients.cost_per_unit.
  Edited on create/update of the ingredient (master form).
  Ingredient ADJUST does not touch cost.
  Recipe Excel sets cost only when it CREATES an ingredient.

  Sale consume snapshots LIVE cost_per_unit onto
    inventory_movements.unit_price (recipe_sale row)
    and into requirements[] at consume time.
  recipe_consumptions.snapshot stores BOM qty, not a frozen purchase rate
    of the stock lot.

  Kitchen food-cost report (IngredientController::kitchenReport):
    SUM(rc.quantity * i.cost_per_unit) using LIVE ingredients.cost_per_unit.
    Changing cost_per_unit TODAY restates historical food-cost in that
    report. Sale movement unit_price rows are left as they were.

[VERIFIED] Finished-goods cost today
  inventory_stocks.avg_purchase_price / last_purchase_price
  InventoryService::addStock blends average only for TYPE_PURCHASE
  and TYPE_OPENING (not adjustment_in).
  NestPOS product adjust blends average itself on add+purchase_price
  even though movement type is adjustment_in.
  FBR munafa comments: later kharid must not rewrite past bills.

[VERIFIED] 500 kg × Rs 300 rice
  If posted only via today’s ingredient adjust: stock +500, cost
  unchanged unless someone edits the ingredient master separately.

[PROPOSED] When a stock-in line has a rate (do not invent a second
cost column on ingredient_stocks in v1):
  - Post qty through adjustIngredientStock (existing).
  - Then set ingredients.cost_per_unit to the incoming rate
    (latest purchase), OR compute a weighted average against
    current_stock-before + incoming qty and write that into
    cost_per_unit.
  Latest-price is what the current master field actually is
  (one number). Weighted average would be NEW behaviour inside
  that same field.
  - Store the line rate in ingredient_movements.snapshot
    (existing JSON) so the movement retains the purchase rate
    even though the table has no unit_price column.
  - Historical kitchen report will follow LIVE cost_per_unit
    unless that report is later changed to use snapshot rates.
    That restatement is CURRENT behaviour, not a new bug.

[PROPOSED] If rice is later bought at Rs 330:
  Stock increases; cost_per_unit becomes 330 (latest) or a blend
  (if weighted average is implemented). Past recipe_sale movement
  unit_price stays at whatever was live at sale time. Kitchen
  report totals MOVE if they keep using live cost.

Recommend for v1: latest purchase → cost_per_unit, rate stored in
movement snapshot, do not add avg/last columns yet (that is schema).
Label weighted-average-on-ingredients as a later enhancement that
needs a column or a report change.

11. STOCK SAFETY
================================================================

[VERIFIED] Current holes
  Every NestPOS adjust/opening is a new movement. Re-submit doubles qty.
  Ingredient opening has no alreadyStocked guard (FBR product form does).
  Product adjust type=set can overwrite to an absolute qty.
  Ingredient adjust is delta-only (cannot “set 500” in one field) —
    safer against overwrite, still doubles if posted twice.
  Recipe import is upsert (safe to re-upload for BOM).
  Stock-check post is blocked when the check is no longer open.
  FBR new purchase always new PUR- number; no file hash.
  Recipe/product Excel: whole file one transaction (all or nothing
    after row skips). Stock adjust is one row per HTTP request.
  Ingredient cannot go below zero on adjust; sales of recipe items
    throw on insufficient kitchen stock.
  Product sales are allowed negative (warnings), NestPOS book says
    sales are never blocked by finished-goods stock.

[PROPOSED] Idempotent stock-in without a new table
  Require a Reference (supplier bill no / file id) on the batch.
  Write ingredient_movements.reference_number =
    "STOCKIN:{reference}:{ingredient_id}" (or product equivalent).
  Before post, refuse if that reference_number already exists for
  the company. Retry after failure of an uncommitted batch posts
  nothing twice; retry after a successful post is a no-op.

  Other rules:
  - Never use type=set for bulk receive.
  - Never post unmatched rows.
  - Unit on the file must equal ingredients.unit (no silent convert).
  - Qty must be > 0.
  - Multi-branch: branch required; actorCanUse enforced.
  - Partial file: post only MATCHED+cleared rows in ONE transaction;
    leave the rest unposted (stock-check style), do not skip-and-commit
    silently the way recipe import skips BOM errors.
  - Do not update Product/Recipe/Ingredient names from a stock file.

15. MASTER EXCEL vs STOCK-IN EXCEL
================================================================

Compare

A) One Excel for Product + Ingredient + Recipe + incoming stock
B) Master Excel (Product/Ingredient/Recipe) + Stock-In Excel

[VERIFIED] Current importers already separate catalog/BOM from qty:
  Product Excel has no stock.
  Recipe Excel creates ingredients at current_stock = 0.
  Stock-check Excel is a third file.

[VERIFIED] Re-uploading Recipe Excel is idempotent for BOM and would
be catastrophic if it also added 500 kg every time.

Recommendation: B.

  MASTER (one sheet): create/update products, ingredients, BOM.
    Safe to re-upload. No qty-in. Optional min_stock threshold only.
  STOCK-IN (second file): dated, referenced, branch-scoped receipts.
    Posted once. Matched to master. Never edits recipe qty or product price.

A single combined sheet would mix MASTER DATA with STOCK TRANSACTIONS
and RECIPE/BOM (see §16). That is the failure mode the current
architecture already avoided.

16. REAL-WORLD EXAMPLES
================================================================

Setup (MASTER DATA, not stock)
  Ingredient Rice    code RICE-25  unit kg  cost 300  stock 0
  Ingredient Chicken code CHK-01   unit kg  cost 650  stock 0
  Ingredient Oil     code OIL-20   unit ltr cost 550  stock 0
  Product Chicken Biryani  recipe: Rice 0.25 kg per plate
  (If the shop writes 250 g on a kg ingredient, consume will deduct
   250 kg per plate. Units must match. [VERIFIED] no conversion.)

1) 500 kg Rice received
   [PROPOSED] Stock-In row matches RICE-25 or name+unit Rice|kg.
   Post adjustIngredientStock +500, snapshot rate 300, cost_per_unit 300.
   current_stock 500; ingredient_stocks[branch] +500.
   [VERIFIED today] same qty via Adjust modal, cost left unchanged
   unless edited on the ingredient card.

2) 200 kg Chicken received
   Same as (1) for CHK-01.

3) 100 ltr Oil received
   Unit on file must be ltr. “100 liters” parsed as ltr alias [PROPOSED].
   “100 ml” vs master ltr → UNMATCHED, do not convert.

4) New ingredient not previously known (Tomato Sauce TOM-99)
   [PROPOSED] UNMATCHED / Needs Clearance. Do not auto-create.
   Owner adds it on Ingredients page or Master Excel, then maps.
   [VERIFIED contrast] Recipe Excel WOULD auto-create it at stock 0.

5) Same supplier item next month

If I am running a restaurant and receive bulk stock from suppliers,
what is the easiest and safest way for me to bring that stock into
NestPOS, have it automatically match my Ingredients, clear exceptions,
and correctly update branch stock without ever corrupting
Product / Recipe / Ingredient master data?

  1. Put Rice / Chicken / Oil on the Ingredient Master first
     (or Master Excel). Give each a stable Ingredient Code.
     Write recipes in kg/g/ltr that MATCH that unit.
     Do not put received quantities on that master sheet.

  2. Keep using Ingredients → Adjust Stock for a single bag
     that arrives at the door.

  3. For a distributor workbook, use a SEPARATE Stock-In Excel +
     clearance screen that:
       - matches Ingredient Code, then exact name+unit
       - never fuzzy-matches
       - never auto-creates ingredients (unmatched = clearance)
       - never edits recipes or product prices
       - requires Branch when I have more than one shop
       - requires a bill/reference so the same file cannot post twice
       - posts through the EXISTING
         RecipeInventoryService::adjustIngredientStock
         (and product adjust for non-recipe retail items)

  4. Do not use FBR “Receive Stock”, DI purchase-orders, or
     Stock-Check Excel for this. Those are different catalogs or
     count-variance, not kitchen receipts.

  5. After post, 500 kg rice is on ingredient stock. Selling 100
     Biryani that need 0.25 kg rice each consumes 25 kg. The dish
     itself has no finished-goods pile.

That is the easiest path that fits the code that already exists.
A brand-new purchase/GRN subsystem would duplicate the kitchen
ledger without making matching safer.
