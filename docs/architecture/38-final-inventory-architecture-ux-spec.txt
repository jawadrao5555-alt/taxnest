3. ONE-SHEET MASTER EXCEL — EXACT FORMAT (chosen)
================================================================

Compared formats
  A. Keep today’s TWO files (product Excel + recipe Excel)
  B. Recipe-shaped sheet only (BOM lines; infer products)
  C. Row Type sheet PRODUCT | INGREDIENT | RECIPE
     (investigation inventory-single-sheet-receipt-control §8)

[CHALLENGE] Format B looks simpler but cannot represent a sellable
item with no recipe (Coke, water). Recipe Excel today also
AUTO-CREATES ingredients (IngredientController::importRecipes) which
is acceptable for MASTER and forbidden for STOCK-IN.

[CHALLENGE] Investigation §8 put “Cost per Unit” on RECIPE rows
because recipes_template.xlsx has that column. Current importer
applies cost ONLY when creating an ingredient, never on reuse
(IngredientController::importRecipes ~577–590). Dual cost writers
(RECIPE row vs INGREDIENT row) would surprise the owner.

[SPEC] Format C, tightened.

Sheet name: Master
File: nestpos_inventory_master.xlsx
One sheet. Never CSV as the default (Pizza Master 8.9E+12 —
PosController::downloadProductTemplate comments).
SKU / Product Code / Ingredient Code columns: Excel TEXT.

Header row 1 (exact titles; importer must also accept aliases)

  A  Row Type
  B  Product Name
  C  Product Code
  D  Price
  E  Category
  F  Description
  G  Tax Rate %
  H  Unit (UOM)
  I  Tax Exempt
  J  Third Schedule
  K  Ingredient Name
  L  Ingredient Code
  M  Ingredient Unit
  N  Cost per Unit
  O  Min Stock
  P  Quantity Needed
  Q  Active

Row Type (required): PRODUCT | INGREDIENT | RECIPE
  (case-insensitive; Urdu/English aliases later if needed)

Which columns apply
  PRODUCT:    B–J, Q
  INGREDIENT: K–O, Q     (N Cost per Unit lives HERE only)
  RECIPE:     B, C, K, L, M, P, Q
              Quantity Needed = per 1 sold unit
              RECIPE must NOT write cost_per_unit
              RECIPE may create a missing ingredient at cost 0
              if and only if no match; owner then edits cost on
              the INGREDIENT row or the Ingredients screen

Matching (reuse existing precedence)
  Product: barcode → SKU → name
    PosController::importProducts
    IngredientController::importRecipes (code then name)
  Ingredient: Ingredient Code (exact, company, case-insensitive)
              else name|unit exact (PosRecipeExcelImportTest
              test_existing_ingredient_reused_by_name_and_unit)
  Recipe: unique (product_id, ingredient_id) upsert quantity_needed
    ProductRecipe unique index

  Qty on hand, opening stock, received qty, supplier, PO/PUR number,
  branch, rate-as-purchase, receipt printer flags, stock-check counts.

Sample rows: prefix Product Name or Ingredient Name with “Misal:”
  [VERIFIED] RECIPE_SAMPLE_MARKER in IngredientController

Caps
  Product creates: same 5000 data-row family as importProducts
  Recipe lines: RECIPE_IMPORT_MAX_ROWS = 2000 today; raise only with
  a test, do not silently mix caps.

Gates
  PRODUCT rows: excel_enabled (PosController::planGate)
  INGREDIENT / RECIPE rows: feature:recipes
  Whole file refused if recipes off and any RECIPE/INGREDIENT row
  is present.

Idempotency of MASTER re-upload
  PRODUCT match → update catalog fields, never add stock
  INGREDIENT match → update name/unit/cost/min/active/code
                    never call adjustIngredientStock
  RECIPE match → update quantity_needed (+ recipe_version increment
                 as importRecipes already does)

6. MATCHING HIERARCHY
================================================================

[VERIFIED] What identity actually exists
  ingredients.code nullable, app-level duplicate check, NO unique index
    IngredientController::store / update
  ingredients.name + unit  (recipe import key)
  No ingredient barcode
  No supplier_item table
  pos_products.sku / barcode / name
    PosController::importProducts

[CHALLENGE] Audit 37 v1 “on first clearance, write supplier code
into empty ingredients.code”. That silently turns a distributor SKU
into the shop’s canonical code. IngredientController treats code as
the shop identity. Two suppliers, or a shop that already uses ING-001,
get collisions. Do not auto-write.

[SPEC] Stock-In match order (company-scoped)

  INGREDIENT lines
    1. NestPOS Code exact, case-insensitive, unique-in-company
       If 0 hits → try 2. If 2+ hits → AMBIGUOUS (no unique DB index)
    2. Exact name + unit (strtolower trim), same as
       importRecipes $ingByNameUnit
       Unit on the file MUST equal ingredients.unit
       (no kg↔g; RecipeInventoryService ignores conversion_factor)
    3. Stop. Never name-only. Never fuzzy.
       Recipe import’s name-only fallback when unit is blank is
       too loose for stock. [CHALLENGE of copying importRecipes]

  ITEM lines
    1. NestPOS Code against barcode then SKU
    2. Exact name
    3. Stop. No fuzzy.

  Supplier Item Code is NOT primary identity in v1.
  It is shown on the clearance row so a human can recognise RICE-25.
  Optional: tick “Save as Ingredient Code” only if ingredients.code
  is empty AND the uniqueness check used by IngredientController passes.
  Default off.

Confidence
  step 1 unique hit = MATCHED (auto-tick, still listed)
  step 2 unique hit = MATCHED
  2+ hits / unit mismatch / zero hits = NEEDS CLEARANCE or INVALID

11. COST HANDLING
================================================================

VERIFIED CURRENT BEHAVIOR
  Kitchen
    ingredients.cost_per_unit is the only cost field
    IngredientController::adjustStock does NOT change it
    IngredientController::update does (master edit)
    importRecipes sets cost only on CREATE
    consumeForInvoice snapshots live cost onto
      inventory_movements.unit_price (type recipe_sale)
    kitchenReport: SUM(recipe_consumptions.quantity * i.cost_per_unit)
      LIVE cost × historical qty — restates history if cost changes
      IngredientController::kitchenReport ~86–104

  Finished goods (NestPOS)
    inventory_stocks.avg_purchase_price / last_purchase_price
    PosInventoryController::adjustStock on add+purchase_price
      weighted average + last
    Movement type remains adjustment_in (not TYPE_PURCHASE)
    InventoryService::addStock blends only for purchase/opening
      (FBR path)

PROPOSED FUTURE BEHAVIOR
  [CHALLENGE] Audit 37 “v1 always write latest rate into
  cost_per_unit” would make every rice delivery restate the kitchen
  food-cost report. That contradicts current adjust, which leaves
  cost alone.

  [SPEC] Stock-In default = qty only, cost unchanged
    (same as today’s ingredient adjust).

  Optional per-batch checkbox: “Also update ingredient cost”
    If ticked: write Rate into ingredients.cost_per_unit (latest).
    Always store Rate in ingredient_movements.snapshot JSON
    even when the checkbox is off, so the movement remembers kharid.

  ITEM lines with Rate: use the SAME weighted-average block as
    PosInventoryController::adjustStock add+purchase_price.
    Never type=set. Never TYPE_PURCHASE.

  Do not add avg/last columns to ingredient_stocks in v1 (schema).

[OWNER] Default of the cost checkbox (off vs on).
[OWNER] Whether kitchenReport should later use snapshot rates

13. STOCK SAFETY
================================================================

[SPEC] Hard rules

  1. Master Excel never calls adjustIngredientStock / addStock.
  2. Stock-In never inserts pos_products, ingredients (except the
     owner left the screen and created one), or product_recipes.
  3. Stock-In never uses adjust type=set.
  4. Qty must be > 0. Unit must equal master unit.
  5. Unmatched / INVALID never post.
  6. Multi-branch: explicit branch + actorCanUse.
  7. Kitchen stock cannot go below zero on adjust
     (already thrown in adjustIngredientStock).
  8. Do not post TYPE_PURCHASE / PurchaseOrder from NestPOS Stock-In.
  9. One DB transaction per Post of the selected MATCHED rows.
 10. TEXT codes; .xlsx only as the shop-facing file.
 11. Cashiers cannot Post.
 12. Do not send NestPOS kitchen files to /fbr-pos/stock/purchase.

[VERIFIED] Ingredient opening on the create FORM still posts
through adjustIngredientStock — keep that; do not also put opening
on Master Excel (would double on re-import).

DEFINITIVE ANSWER
================================================================

If we want the easiest and most powerful Inventory Management
system for a restaurant, with Products + Ingredients + Recipes
managed together and bulk stock safely received through Excel,
what exactly should we build?

  Build TWO Excel files and ONE new screen, on top of the ledgers
  that already exist. Do not build a purchase/GRN engine.

  1. Inventory Master.xlsx (one sheet, Row Type
     PRODUCT / INGREDIENT / RECIPE)
     Creates and updates the menu, the kitchen catalog, and the BOM.
     Safe to re-upload. Never posts stock.

  2. Inventory → Stock In (new page beside Stock Check)
     + StockIn.xlsx
     Matches supplier lines to existing ingredients/items
     (code, then exact name+unit), clears exceptions by picking
     an existing master row, then Posts through
     RecipeInventoryService::adjustIngredientStock and the existing
     product Adjust-add path.
     Requires Branch when there are branches, and a bill Reference
     so the same file cannot land twice.

  3. Leave in place: Ingredients Adjust for one bag, item Adjust
     for one crate, Transfers, Stock Check, FBR Receive Stock
     (FBR catalog only).

  That is the whole system: master data on one sheet, stock
  transactions on another, sales already consuming recipes into
  ingredient stock.

End of spec. No implementation performed.
