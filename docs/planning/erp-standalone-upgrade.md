# Upgrade a standalone account to an ERP

Apply this requirement when building Lab, School, Hospital and future ERPs. A customer already operating on a standalone product should be able to request an ERP, keep access to the original account and bring across the records needed to start work. Each ERP defines which source products, records and capabilities it supports. This document records the design for future implementation.

## Current behavior

| Operation | What the application does today |
| --- | --- |
| Admin changes a company’s product | The routed [product transition controller](../../app/Http/Controllers/SaasAdmin/AdminProductTransitionController.php) requires a super-admin and a compatible target package or trial. The [pristine check](../../app/Services/ProductTransitionCompatibility.php) rejects a company with company-owned history, configuration or access records outside the company and user tables. A successful change keeps the company key, checks target login conflicts and updates the product scope of its users. |
| Admin creates a sibling product account | The same controller creates a separate company, copies profile fields and sets up one owner login and a separate trial. The company group connects the business accounts. Existing users, branches, transactions and device pairing stay with their source account. The current Healthcare clone defaults to the Clinic organization type. |
| Standalone POS enables PRA integration | The [POS controller](../../app/Http/Controllers/PosController.php) checks for NTN and switches the POS integration mode on the same company. This enables the PRA setup path within POS. |
| Healthcare imports setup data | The [Healthcare importer](../../app/Services/HealthOnboardingImportService.php) uses module-aware spreadsheet templates, preview and revalidation of the stored file at commit. Natural keys support safe repeats. It covers setup and master data such as staff, patients, service catalogs and opening stock. Visits, prescriptions and diagnoses stay in the original clinical system. |

## Eligibility and identity

- Let the owner request an upgrade by source Company ID from their account or through a SaaS admin acting within their role. Resolve the public product ID, any historical product alias, the original account code and the numeric key to the same company wherever those identifiers are accepted. A successful lookup identifies a record. Company and branch authorization still apply.
- Require the exact destination ERP, organization type and package. Check source and destination ownership, product and package availability, branch and module allowances, and any existing sibling in that ERP. Reuse a compatible existing destination after explicit confirmation, and serialize provisioning so repeated approval cannot create extra accounts.
- Preserve the source numeric company ID, user and branch links, legacy account code, prior product IDs, receipts and existing subscriptions. For an operating source, create or reuse an ERP sibling with its own numeric key, product-specific display ID and entitlement. Pristine moves continue through the existing guarded flow. Allocate new product display identifiers through the same registry used by the company lifecycle.
- Preserve the source Desktop Agent’s numeric company identity, API key, signed device scope, offline queue and printer mappings. The ERP can pair its own authorized devices under its own numeric company and branch scope when the target supports them. Keep secrets out of the import and credential handoff.

## Mapping and cutover

1. **Map each source product.** Maintain a supported source-to-target map per ERP and source edition. Source modules and history differ. School may map students, guardians, campuses and reconciled unpaid fees. Lab may map clients, test catalogs, collection centres and approved balances. Hospital may map patients, services, departments, approved stock and opening balances. Separate data types that can be copied, must be transformed or require archive access. Review clinical records, school records and staff data against the destination’s access rules and the data owner’s approval.
2. **Resolve records to the destination.** Create or map destination branches and campuses explicitly. Map users to new role, branch and department assignments and invite them through normal access controls. Validate destination package limits. Retain each source record ID as provenance in a mapping ledger. Receipt relationships and source audit entries stay available through the original company.
3. **Preview before committing.** Save an authorized snapshot or export, with source scope, required mappings, cutoff time and an immutable fingerprint. Show proposed row counts, duplicates, unresolved references, rejected rows, and control totals for balances, inventory and outstanding items. Confirm which accounts and branches the transfer affects. Revalidate the same snapshot and target prerequisites at commit.
4. **Make retries safe.** Persist one migration request per source, target, cutoff and snapshot. Give every row a durable source identity and track its destination ID. Use atomic writes for dependent records, same-company locks for conflicting runs and checkpoints for partial failures. Resume or retry from the stored request. A repeated import must preserve counts and balances. A changed snapshot or mapping requires a fresh preview.
5. **Agree when each system starts writing.** Keep the source operating until the owner confirms the cutoff. Capture changes since the first preview and reconcile them before switching. Decide whether the source continues independently or transitions to read-only archive access. Preserve historic invoice numbers, fiscal references and acknowledgements in the source. Destination opening records and historical references must use a non-dispatch path. New ERP sales begin in the approved period under the ERP’s own numbering and verified fiscal setup. Fiscal credentials, submission state and pending queues are reconciled per product so the same sale cannot be submitted twice.
6. **Close the migration in Support.** Record requester, approval, timestamps, source/destination IDs, selected package, mapping version, totals and cutover state. Show the operator how to find the original account, resume a failed transfer or escalate an unresolved item. Recover pre-cutover failures by keeping the source authoritative and reversing only pre-approved destination setup changes. Corrections after the destination has new activity require a recorded reconciliation and review.

## Acceptance for each ERP

- Use synthetic cases for two companies and at least two branches or campuses. Exercise unauthorized company and branch IDs, wrong package or module, mismatched identity and duplicate sibling requests.
- Verify existing numeric IDs, account codes and old product aliases continue to resolve. Test original login, user permissions, historical invoice and report access, Desktop Agent pairing, queued transactions and printers before and after provisioning.
- Check import counts, financial totals, stock, duplicate handling, interruption and retry, reporting permissions and cutoff rules. Verify an original fiscal document remains traceable and a copied historical row cannot dispatch it again.
- Verify the destination package and fiscal modules independently. External adapters use separate, tenant-scoped credentials and belong to the ERP for which their capability and authorized contract are verified.
