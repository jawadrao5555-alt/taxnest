# Optional POS WhatsApp auto-send

Owner requirements: auto-billing opt-in ON/OFF (default OFF), package/add-on authorization on the server, preserve manual wa.me sharing and optional browser auto-open. This PR covers PRA POS (`pos_transactions`), including restaurant settlement and provisional promotion through model finalization; DI/FBR POS behavior is unchanged.

Compatibility matrix: default OFF/manual existing -> no outbox/no provider call; opted-in final with valid phone -> one durable row; draft/deliberate provisional/cancelled/archived/bad phone -> no send; provisional becomes final -> enqueue once; payment rollback -> outbox rolls back; duplicate saves/callbacks/workers -> atomic claim prevents duplicate send; opt-out/package downgrade/cancellation/recipient change before drain -> cancel; transient rate limit -> bounded scheduled retry; ambiguous timeout/5xx/process death -> UNKNOWN, never blindly resend; signed same-company/Meta-number webhook -> forward-only status, early callback persisted for reconciliation; foreign/unsigned callback -> cannot change POS status. Saved manual toggles, provider credentials on blank input, tax/payment/printing and existing DI API paths remain intact.

A separate typed POS provider adapter uses the existing Meta graph endpoint/approved English four-parameter invoice template and the actual POS public PDF route (no DI `/pdf` suffix). Each opted-in company needs its own verified Meta number/token, approved template and App Secret. Secrets never populate forms or validation old-input. New flag has default false and no bulk opt-in/backfill. Auto-send applies to new finalized bills; enabling does not scan old billing.

Model-finalization inserts an idempotent outbox row inside the invoice transaction. Best-effort after-response drain is backed by `pos:whatsapp-drain --limit=5` every minute; it requires the existing scheduler to run. A dead worker does not lose the row. Provider response acceptance is SENT, not customer delivery. Signed callbacks on the configured phone update DELIVERED/READ. New status inbox retains minimal status events for 30 days and handles callback-before-HTTP-response races. UNKNOWN requires owner/provider history review/manual share, because no provider idempotency guarantee is assumed. No automatic resend of ambiguous outcomes.

Local PHP/Chrome/MariaDB unavailable, so these are required fresh CI evidence, not local pass claims. No real WhatsApp recipient/provider credentials, production access, owner merge/deploy or actual customer delivery claimed.
